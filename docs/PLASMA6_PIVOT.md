# ADR: Canopy Plasma 6 pivot — 2026-11-27

Status: owner-authorized development direction; implementation and release acceptance NOT RUN. This document supersedes incompatible implementation priorities for new work on the Plasma integration track, not existing release/security gates or historical evidence.

## Decision and boundaries
Use upstream Plasma 6 and KWin, Qt 6/KF6 and their native extension points. Do not fork KWin/Plasma, run a second compositor, retain a redundant complete shell, duplicate upstream services, or turn a standalone ApplicationWindow into a fake desktop. Keep Canopy product identity and original Classic/Modern/future Shell Packs. Use Kubuntu 26.04 LTS as an isolated reference guest, not a final LacOS distribution decision. Prefer evaluating a minimal Ubuntu LTS + distribution-supported Plasma 6 foundation against Kubuntu LTS and Mint-based alternatives; select on evidence rather than inherited branding. Mint 22.3 uses Noble, whose normal Plasma packages are 5.27; never mix incompatible repositories. Reassess final distro based on supported update/security lifecycle, upstream package compatibility, hardware, resource and recovery evidence.

Preserved baseline: integration/canopy-classic-20261123 at ec910d7a7275296ecbc8b5e5c459d356205165d1; new integration target integration/canopy-plasma6-20261127. Keep main, all prior branches, PRs, commit history, tests, evidence and original assets. Do not force-push, abandon uncommitted work, or close old PRs indiscriminately. Finish every currently assigned task before reassigning its agent: complete implementation, tests, independent review, pushes and eligible legacy integration. If genuinely externally blocked, preserve recoverable work and an explicit blocker rather than claiming completion. No new Cinnamon-specific assignments; freed workers may prepare the migration while existing assignments finish. Capture the final legacy integration SHA in an archival tag (not a release); audit and selectively port subsequent verified changes since the Plasma branch point. Classify each as reuse/port/reference/defer/superseded. Do not overwrite prior baseline or copy unverified branches blindly.

## LacOS architecture expansion (owner decision)
The final LacOS production core must be read-only and atomically updated, with APT, Pacman, Flatpak and rootless Podman application options; do not mix host package managers. Canopy Modern uses Zorin OS as a usability/design reference without importing another desktop or copying proprietary assets. See [LACOS_IMMUTABLE_ARCHITECTURE.md](LACOS_IMMUTABLE_ARCHITECTURE.md) and [LACOS_VISION.md](LACOS_VISION.md). The immutable base and update backend remain evidence-gated; KDE neon is an additional latest-upstream test lane, not a mandated production base. Preserve current assignments and prioritize native Classic; distribution research is independent and bounded.

## Execution order
1. Inventory exact source and PR dependencies, original assets and license provenance; identify upstream substitutes, portable code and adapters. Keep a machine-readable migration matrix with evidence and exact SHAs. Prioritize executable work over expanding offline validation.
2. Establish a disposable Plasma 6 guest; verify ISO/source, packages, versions, GPU, Wayland session, baseline Cinnamon guest, logs and screenshots. Preserve existing Mint VM; use snapshots; do not modify host OS desktop, credentials or production systems. Start with distribution-supported packages and no extra PPAs.
3. Build a genuine Plasma 6 native Classic vertical slice: versioned plasmoid metadata, PlasmoidItem/containments, native top panel, floating dock, wallpaper, approved original icons, keyboard access and real window/application operations. Use upstream task manager and launch services (verify API stability and compatibility), not synthetic running-window state. Reuse QML items after extracting them from ApplicationWindow; preserve originals and optical corrections. Use actual Plasma session screenshot evidence.
4. Integrate existing upstream notification, tray, network, power, lock, display, launcher and settings services; use global menu when supported and a local-menu fallback. Avoid duplicate app index, notification daemon, power daemon, compositor or always-running preview. Use narrow adapters; prefer upstream stable APIs; isolate version-sensitive imports. Do not claim unsupported application behavior.
5. Package reversible user/session deployment using ownership-aware installs/uninstalls, backed-up layouts, no destructive resets or arbitrary scripts from untrusted packs. Keep native fallback desktop, preserve data, test upgrade/rollback/crash/restart/suspend and real application state.
6. Build Modern as another presentation on the same stack. Implement a trusted built-in Shell Pack manager, per-pack preferences, prepare/apply/verify/rollback lifecycle, monitor-aware layouts, no simultaneous full shells. Test repeated switches with apps open and no data loss or unbounded memory. Never describe layout scripts as sandboxing. Third-party executable QML/JS disabled until separate provenance/signing, isolation and permissions gates pass; no arbitrary community code execution.
7. Benchmark stock Mint, existing Canopy preview (clearly labeled), stock Plasma and minimal Plasma+Canopy on equal hardware and comparable workload. Measure system memory (available/used methodology), shell-process PSS, idle CPU, GPU, wakeups, boot/startup, responsiveness, power and sustained memory growth. Keep <=200 MiB incremental shell-owned PSS and <=1% idle CPU targets; verify full-system efficiency without disabling security/accessibility or essential functionality. Record versions, backend, exact SHA, commands, sample duration, raw logs; 5-minute idle, repeated cold boots, 24-hour soak and 100 round-trip switches where applicable. No claim of superiority before data.
8. Select LacOS immutable distribution and update backend after working Classic, Modern and switching; independent research may start sooner; no ISO release until packaging, update, hardware, security, resource, recovery and owner visual gates pass.

## Owner-approved trunk transition and release separation
- During migration, retain main as the protected reference; integrate verified work into the respective legacy or Plasma integration branches. Do not promote partial or broken architecture to main.
- Once native Plasma Classic forms a coherent installable baseline, validate actual guest login/session or reversible deployment, real app launching/focus/dock/window operations, single compositor and service ownership, safe rollback, applicable resource/security/accessibility checks and exact-SHA integrated regression evidence. Preserve prior main and final legacy SHAs with archival tags; no force pushes.
- Hermes is authorized to open, independently review and merge a baseline transition PR into protected main without further routine approval only when these gates pass and required checks/reviews are enforced and satisfied. Protected artwork/identity changes, named PR holds (#279/#151/#278), high-risk approvals and owner final visual acceptance remain binding where applicable. If a gate or protection cannot be verified, keep the transition blocked and report it; never bypass protections.
- After transition, main is the continuously integrated development trunk, not a release. Feature PRs may start draft; promote and merge independently reviewed verified changes after current-base/merge-result checks, applicable regressions and security/performance/visual scope checks. Serialize conflicting merges or use a merge queue where available; run post-merge regression, revert or repair regressions promptly. No direct unreviewed pushes, self-review substitution, failed/skipped required checks, force pushes or stale-head merges. Branch protection configuration must be verified; if unavailable request the specific administrative action rather than weakening controls.
- Stable releases, public release tags/ISOs and substantial protected visual changes require explicit owner approval and all applicable release gates. Archival tags are non-release references. Update all governing docs and supervisor queues to match this policy, avoiding permanent draft accumulation and circular pre/post-merge gates.
